## 6. Gaps & Bugs

### BUG-1: Silent Socket Fallback (Gap 24.2)
*   **Priority**: 🟠 **High** | **Impact**: Combat Precision
*   **Description**: `GetSocketLocation` falls back to character center if a socket is missing. This causes invisible traces that hit targets inside the player or nothing at all. Logging an `Error` but still returning a fallback location (`OwnerCharacter->GetActorLocation()`) is misleading; the trace function should explicitly handle this as a critical failure.
*   **Fix**: Fail the trace loudly with an `Error` log and skip `PerformWeaponTrace` for that frame if sockets are missing, or return a failure flag.
    ```cpp
            if (OwnerCharacter)
            {
    -           UE_LOG(LogWeaponComponent, Error, TEXT("[%s] Socket '%s' not found on character or weapon mesh! "
    -               "OwnerMesh=%s, SpawnedWeapon=%s. Returning actor location as fallback - hit traces will be inaccurate."),
    -               *GetNameSafe(GetOwner()), *SocketName.ToString(),
    -               OwnerMesh ? *OwnerMesh->GetName() : TEXT("null"),
    -               SpawnedWeaponMesh ? *SpawnedWeaponMesh->GetName() : TEXT("null"));
    -           return OwnerCharacter->GetActorLocation();
    +           UE_LOG(LogWeaponComponent, Error, TEXT("[%s] Socket '%s' not found on character or weapon mesh! OwnerMesh=%s, SpawnedWeapon=%s. Trace will be inaccurate."),
    +               *GetNameSafe(GetOwner()), *SocketName.ToString(), OwnerMesh ? *OwnerMesh->GetName() : TEXT("null"), SpawnedWeaponMesh ? *SpawnedWeaponMesh->GetName() : TEXT("null"));
    +           return OwnerCharacter->GetActorLocation(); // Consider returning FVector::ZeroVector or an invalid flag.
            }
            // No owner character and socket not found. This is a critical error.
    -       UE_LOG(LogWeaponComponent, Error, TEXT("Socket '%s' not found and no owner character! Returning zero vector."),
    +       UE_LOG(LogWeaponComponent, Error, TEXT("[ERROR] Socket '%s' not found and no owner character! Cannot perform accurate trace."),
                    *SocketName.ToString());
            return FVector::ZeroVector;
    ```

### GAP-1: High-Speed Misses (HIT-1 / Gap 24.1)
*   **Priority**: 🔴 **Critical** | **Impact**: Combat Reliability
*   **Description**: `PerformWeaponTrace` performs a single sweep per tick. At high angular velocities (swinging fast) or low frame rates, the arc between frames is not covered, allowing targets to "pass through" the blade.
*   **Fix**:
    *   **Rationale**: Sub-stepping ensures the entire swing volume is sampled.
    *   **Snippet**: Implement a `TraceSubSteps` loop in `PerformWeaponTrace`.
        ```cpp
        const int32 SubSteps = 3; 
        for (int32 i = 1; i <= SubSteps; ++i) {
            float Alpha = (float)i / SubSteps;
            FVector MidStart = FMath::Lerp(PreviousStart, CurrentStart, Alpha);
            FVector MidEnd = FMath::Lerp(PreviousTipLocation, CurrentTipLocation, Alpha);
            // ... Perform sub-trace
        }
        ```

### GAP-2: Missing Hit Metadata (Gap 24.3)
*   **Priority**: 🟡 **Medium** | **Impact**: VFX/Juice
*   **Description**: `ProcessHit` doesn't capture `WeaponVelocity`, `AnimationTime`, `HitPhase`, or `DistanceToTarget`. This makes it impossible to scale blood splatter or sync impact VFX to the exact animation frame.
*   **Fix**: Expand `FHitReactionInfo` struct and populate it during `ProcessHit` using `OwnerMesh->GetSocketVelocity()`.

### GAP-3: Velocity-Based Prediction (Gap 24.7)
*   **Priority**: 🟡 **Medium** | **Impact**: Accuracy
*   **Description**: The trace is reactive; it doesn't account for where the target *will be* during the sweep interval.
*   **Fix**: Integrate `UPhysicsIntegrationLibrary::PredictFuturePosition` to expand the trace volume based on target velocity.

### GAP-4: Hit Validation
*   **Priority**: 🟡 **Medium** | **Impact**: Robustness
*   **Description**: Missing validation logic to ensure hits are registered correctly within the intended hit window.

### GAP-5: Redundant `WeaponData` resolution logic in `BeginPlay`.
*   **Priority**: 🟠 **High** | **Impact**: Code Readability / Maintainability
*   **Description**: The `WeaponData` resolution logic in `BeginPlay` duplicates the fallback pattern. `InitializeFromWeaponData` already handles the null case. The multiple `if (!ResolvedWeaponData)` blocks and `UE_LOG` calls make the function verbose and prone to errors.
*   **Fix**: Simplify `BeginPlay` to directly call `InitializeFromWeaponData` with the `WeaponData` member, and let `InitializeFromWeaponData` handle the resolution internally.
    ```cpp
        // Initialize from resolved weapon data
    -   if (ResolvedWeaponData)
    -   {
    -       InitializeFromWeaponData(ResolvedWeaponData, true);
    -   }
    +   // Initialize from WeaponData, or if null, attempt to resolve from CombatSettings.
    +   // InitializeFromWeaponData handles null internally.
    +   InitializeFromWeaponData(WeaponData, true);
    }
    ```
