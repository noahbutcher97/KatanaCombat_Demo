# Code Review: AnimNotify_HoldWindowStart.h (2026-02-06)

## 1. Objective
Triggers the start of a "Hold Window" as a single, event-driven AnimNotify. This is the **NEW** mechanism for hold mechanics.

## 2. Scope
Public API for the `AnimNotify_HoldWindowStart`, including its design philosophy and configuration.

## 3. Metrics & Standards
*   **Metrics**:
    *   Complexity: Low.
    *   Test Coverage: N/A (Declarations only).
*   **Standards Adherence**:
    *   Style & Naming: 🟢.

## 4. Code Organization
*   **Module Clarity**: High (Animation Notify).
*   **Component Cohesion**: High (Single purpose, event-driven).
*   **Dependency Flow**: Minimal (Triggers event on `CombatComponent`).

## 5. Key Areas
*   **Design Philosophy**: Clearly articulates the **shift from state-based `AnimNotifyState` to event-based `AnimNotify`** for hold detection. This improves robustness and simplifies logic by centralizing timer management in `CombatComponent`.
*   **Functionality**: Allows designers to specify *when* hold detection begins for both light and heavy attacks, with different behavior paths (ease slowdown vs. charge loop).

## 6. Gaps & Bugs

### GAP-1: Contextual `InputType` Validation
*   **Priority**: Low | **Impact**: Designer Error
*   **Description**: `InputType` can be set to any `EInputType`, but only `LightAttack` or `HeavyAttack` are valid for hold mechanics. A designer could mistakenly select `Block` or `Evade`.
*   **Fix**:
    *   **Rationale**: Improve designer experience and prevent misconfiguration.
    *   **Action**: Implement `meta=(EditCondition="InputType == EInputType::LightAttack || InputType == EInputType::HeavyAttack")` or a custom `UPROPERTY` specifier to limit valid `InputType` selections in the editor.
